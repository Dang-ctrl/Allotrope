# Evidence and provenance

This document describes `allotrope/evidence/`, and — as with every other
claim in this repository — what it does and does not do yet.

## The problem it addresses

The project produces headline numbers ("15.9% fuel reduction", "84.6% less
black carbon") from several different places today: `scripts/run_baseline.py`,
`allotrope/evaluate.py`, `allotrope/evaluate_scenarios.py`. Each computes and
prints its own comparison independently, with no shared record of *how* the
number was produced. `allotrope.experiment.ExperimentTracker` solves this for
training runs (`runs/<run_id>/record.json` with git commit, config, metric
history). Nothing solved it for the comparison/evaluation runs that actually
generate the numbers people quote.

## What's implemented

`allotrope/evidence/`:

- `EvidenceRecord` — a dataclass holding: a unique `experiment_id`, a
  `timestamp`, the `git_commit` and `git_dirty` flag (reusing
  `allotrope.experiment.git_commit`/`git_dirty`, not duplicating them), the
  `station`, the exact list of `seeds` the run used, the `metric_name` and
  `metric_value` that were measured, an optional `baseline_name`/
  `baseline_value` when the metric is a comparison, an optional
  `model_checkpoint` path, `source_script`, a free-text `description` of
  what was measured and how, and an `extra` dict for anything else worth
  keeping (e.g. related metrics computed in the same run).
- `record_result(...)` — builds an `EvidenceRecord` from a script's own
  measured values and writes it to `runs/evidence/<experiment_id>.json`.
  It performs no aggregation: if you pass `seeds=0`, the record says
  `"seeds": [0]`, not "validated across seeds."
- `save_evidence` / `load_evidence` / `list_evidence` — the read/write
  primitives, matching `ExperimentTracker`'s file-based, no-server pattern
  (one JSON file per record, under `runs/evidence/`).

## Wired into one real script

`scripts/run_baseline.py` (`EfficientRuleBased` vs `LegacyNPlusOne`) now
calls `record_result` after it prints its comparison, so every real run of
that script leaves behind a record. This example was generated by an actual
run — `python scripts/run_baseline.py --station maitri --seed 0` — not typed
in by hand:

```json
{
  "experiment_id": "Maitri_fuel_l_saved_1788596803_6c05014c",
  "timestamp": 1788596803.500483,
  "git_commit": "f9c3809aeba38c0c2ed6ced86eabe1047c9ec9b9",
  "git_dirty": true,
  "station": "Maitri",
  "seeds": [0],
  "metric_name": "fuel_l_saved",
  "metric_value": 40352.49039219765,
  "description": "8760 steps at 1h starting 2026-01-01, EfficientRuleBased vs LegacyNPlusOne, scripts/run_baseline.py",
  "baseline_name": "LegacyNPlusOne.fuel_l",
  "baseline_value": 254128.20084815274,
  "model_checkpoint": null,
  "source_script": "scripts/run_baseline.py",
  "extra": {
    "efficient_fuel_l": 213775.7104559551,
    "black_carbon_g_saved": 61180.4048450367,
    "periods": 8760,
    "freq": "1h",
    "start": "2026-01-01"
  }
}
```

Note `git_dirty: true` — this run was made against an uncommitted worktree
during development of this feature, and the record says so honestly rather
than hiding it. A record produced against a clean commit will say
`"git_dirty": false`, which is what should be true for any number that ends
up in a report or slide deck.

Reading this record back answers exactly the question a judge or reviewer
would ask: this number came from station Maitri, seed 0 only, git commit
`f9c3809...`, comparing `EfficientRuleBased` against `LegacyNPlusOne.fuel_l =
254128.2 L`, computed by `scripts/run_baseline.py` over a full simulated year.

## Tests

`tests/test_evidence.py` covers:

- `EvidenceRecord` round-trips through `save_evidence`/`load_evidence` with
  no field loss.
- `record_result` writes the exact station/seed/metric/baseline values it
  was called with — read back from disk, not from the in-memory object.
- `list_evidence` returns every record in a directory, and an empty/missing
  directory returns `[]` rather than raising.
- An end-to-end test actually runs `scripts/run_baseline.py` as a script
  (short horizon, `--periods 48`, in an isolated `tmp_path` cwd) and checks
  the real evidence file it wrote — not a mock of what it should write.

## What's explicitly not done

- **No UI.** There is no "click to verify" surface, no dashboard, no way to
  browse `runs/evidence/` other than reading the JSON files directly. That's
  a deliberately separate, future slice.
- **Not wired into every script.** Only `scripts/run_baseline.py` produces
  evidence records today. `allotrope/evaluate.py` and
  `allotrope/evaluate_scenarios.py` still print their comparisons without
  leaving a durable record — instrumenting them is straightforward (the same
  `record_result` call, same pattern) but hasn't been done in this pass.
- **No cross-run aggregation or statistics.** `list_evidence` returns raw
  records; nothing here computes a mean, a confidence interval, or a
  "validated across N seeds" claim. Building that honestly requires actually
  running multiple seeds and computing the aggregate at the call site first
  — `allotrope.sim.runner.compare_multi` already does mean-across-seeds
  comparison, but no script currently pipes that output into an
  `EvidenceRecord`.
- **No tamper detection.** A record is a plain JSON file; nothing hashes or
  signs it, so it proves what a run *reported*, not that the file hasn't
  been hand-edited since. For a hackathon submission this is an honesty
  mechanism (make numbers traceable), not a security control.
